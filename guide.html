Layer 00

Pixels

A framebuffer is memory you can see.

Open the workbench ↓

You'll write: createFrame, pixelIndex, setPixel, getPixel, clearFrame in src/00-pixels.js

Every frame of the KineticIntro you'll build in layer 09 is 1080 × 1920 pixels. Before anything can move, you need somewhere to put those pixels and a way to change them one at a time. That place is called a framebuffer, and by the end of this layer you'll have written one.

Under the hood

A pixel is three or four numbers

Your screen is a grid of tiny lights. Each one mixes red, green and blue light, and how bright each color glows is a number from 0 (off) to 255 (full). Why 255? Each channel gets one byte: 8 bits, which can hold 2⁸ = 256 different values, 0 through 255.

  [255,   0,   0]  red
  [  0,   0,   0]  black (all off)
  [255, 255, 255]  white
  [ 91, 140, 255]  Motion Studio's blue

A fourth number, alpha, says how opaque the pixel is: 255 is solid, 0 is invisible. Alpha doesn't matter yet, but layer 01 is all about it. So one pixel is 4 bytes: R, G, B, A.

Memory is one long line

A picture is 2-D, but computer memory is a single long row of bytes. So you have to decide how to lay the grid out in a line. Nearly everything (browsers, image files, GPUs) uses the same answer: row by row, left to right, 4 bytes per pixel.

Here's a frame 4 pixels wide and 3 tall, with each cell showing where that pixel starts in the line:

            x = 0   x = 1   x = 2   x = 3
          ┌───────┬───────┬───────┬───────┐
  y = 0   │   0   │   4   │   8   │  12   │
          ├───────┼───────┼───────┼───────┤
  y = 1   │  16   │  20   │  24   │  28   │
          ├───────┼───────┼───────┼───────┤
  y = 2   │  32   │  36   │  40   │  44   │
          └───────┴───────┴───────┴───────┘

  data (one long line, folded to fit):

  [ R G B A  R G B A  R G B A  R G B A
    └(0,0)┘  └(1,0)┘  └(2,0)┘  └(3,0)┘
    index 0  index 4  index 8  index 12
  | R G B A ... ]
    └(0,1)┘
    index 16

Look at the numbers for a while before writing pixelIndex. Going one step right adds the same amount each time. Going one step down adds a different, bigger amount. What is each amount, and why? If you can say that out loud, the formula writes itself.

Why a Uint8ClampedArray

JavaScript has typed arrays: fixed-size blocks of raw numbers, much faster than normal arrays because every slot is the same type. Uint8ClampedArray means:

  • Uint8: each slot is an unsigned 8-bit integer, 0–255. Exactly one channel.
  • Clamped: if you store something out of range, it's pinned to the nearest edge instead of wrapping around. Store 300 and you get 255; store −5 and you get 0; store 127.6 and it rounds to 128. The exact rule is the ToUint8Clamp operation in the ECMAScript specification, the document that defines JavaScript.

The browser uses this exact type for the pixels of a canvas (ImageData.data), which is why you're using it. The HTML standard defines ImageData as RGBA bytes stored left to right, row by row from the top: the same layout you're about to build. Compare it with its unclamped cousin Uint8Array, where 300 wraps around to 44 (300 − 256).

The edge of the world

What should happen if someone calls setPixel(frame, 4, 0, ...) on a frame that's 4 pixels wide? There is no column 4. But the index formula will still happily compute a number, and that number lands somewhere real:

  setPixel(frame, x = 4, y = 0)
  on a 4-wide frame

          x = 0  x = 1  x = 2  x = 3  x = 4?
  y = 0   ░░░░░  ░░░░░  ░░░░░  ░░░░░    ?
  y = 1   █████  ░░░░░  ░░░░░  ░░░░░    ▲
          │                             │
          │          you meant here ────┘
          └─ but the formula points here:
             (0, 1)

This wrap-around bug is real: shapes that hang off the right edge reappear on the left, one row down. setPixel must check bounds itself, and later layers slide things off-screen all the time.

Getting it on screen

Your frame is just numbers in memory. To see it, lib/present.js (provided) wraps them in an ImageData and copies them into a <canvas> with putImageData:

  your frame.data

You don't need to write that part. The important idea is that the screen only ever shows what's in memory, and drawing just means changing numbers.

    Shapes & blending
    
      
    Deciding which pixels a shape covers, and what happens where shapes overlap.
    
      Open the workbench ↓

    Builds on: layer 00
    

    KineticIntro has a glowing radial background, words that fade in and out, and a light sweep that brightens the logo as it passes. All three are this layer: filling shapes, mixing colors, and blending a see-through color over what's already there.
    

    Under the hood
    

    Colors as text: hex
    

    Designers write colors like #5B8CFF (the CSS hex color notation). That's three bytes written in base 16 (hexadecimal), two digits each:
    

      # 5B 8C FF
    │  │  └─ blue  = 0xFF = 15×16 + 15 = 255
    │  └──── green = 0x8C =  8×16 + 12 = 140
    └─────── red   = 0x5B =  5×16 + 11 =  91
    

    JavaScript can read base-16 text for you (look up parseInt's second argument, the radix). There are two common approaches: cut the string into three 2-character pieces, or read all six digits as one number and pull bytes out of it with bit shifts (>>) and masks (& 255). Either is fine. The second shows you how colors are often packed in memory.
    

    Rasterizing: which pixels does a shape cover?
    

    A rectangle from x = 2 to x = 6 is an idea with perfect edges. The screen only has whole pixels. Turning shapes into pixels is called rasterization, and the rule almost every renderer uses is: a pixel belongs to the shape if its center is inside.
    

      rect x = 2 .. 6

    0   1   2   3   4   5   6   7
  ┌───┬───┬───┬───┬───┬───┬───┬───┐
  │ · │ · │ ■ │ ■ │ ■ │ ■ │ · │ · │
  └───┴───┴───┴───┴───┴───┴───┴───┘
            ↑   ↑   ↑   ↑   ↑
  centers  2.5 3.5 4.5 5.5 6.5
           └─── inside ──┘ not
    

    For rectangles, testing centers is the same as rounding the edges, which is what the spec asks for.
    

    The right edge is exclusive (6 is out). This "half-open" rule means two rectangles that share an edge (one from 2 to 6, the next from 6 to 9) meet perfectly, with no gap and no pixel painted twice. You'll see why that matters in Break it.
    

    Study buddy: "Ask me to predict which pixels fillRect(1.5, 0, 2, 1) covers, then tell me whether my reasoning (not just my answer) was right." Ask Claude · Ask ChatGPT
    

    Circles: distance from the center
    

    A pixel is inside a circle if its center is no farther than r from the circle's center. That's Pythagoras: dx² + dy² ≤ r². (You can skip the square root by comparing squared distances. Why does that give the same answer?)
    

      · · · · · · · · ·
  · · · ■ ■ ■ · · ·
  · · ■ ■ ■ ■ ■ · ·
  · · ■ ■ ● ■ ■ · ·
  · · ■ ■ ■ ■ ■ · ·
  · · · ■ ■ ■ · · ·
  · · · · · · · · ·

  every ■ passes  dx² + dy² ≤ r²
  ● = center
  ┌─────────┐  only test pixels
  └─────────┘  inside this box
    

    You could test every pixel in the frame. For a small circle on a 1080 × 1920 frame that's 2 million tests to draw maybe 300 pixels. Instead, only visit the circle's bounding box: from cx − r to cx + r in each direction.
    

    Jagged edges like these are called aliasing. Real renderers soften them with antialiasing: a pixel that's 40% covered gets 40% of the color. See Going further.
    

    Alpha blending: painting with see-through paint
    

    Here's the big one. When you paint a half-transparent red over a blue pixel, the result is a mix. When you paint it over an empty, fully transparent pixel, it should still be red, just see-through.
    

    This was worked out in 1984 by Thomas Porter and Tom Duff at Lucasfilm, in a paper called "Compositing Digital Images" (SIGGRAPH '84, PDF). It's how film effects layered spaceships over backgrounds, and how every browser layers one element over another. Their "over" operation, with alphas written as 0 to 1:
    

      a = alpha of the new color (source)
  b = alpha of the old pixel (destination)

  outAlpha = a + b × (1 − a)
  outRGB   = ( newRGB × a
               + oldRGB × b × (1 − a) )
             / outAlpha
    

    Read it as coverage. The new paint covers fraction a of the pixel. Of what's left, (1 − a), the old pixel covers fraction b. The color is the average of the two, weighted by how much each one covers. The divide by outAlpha turns "amount of light" back into "color".
    

      50% red over opaque blue:
  outAlpha = 0.5 + 1 × 0.5 = 1
  red  = (255×0.5 + 0) / 1   ≈ 128
  blue = (0 + 255×1×0.5) / 1 ≈ 127

  50% red over nothing:
  outAlpha = 0.5 + 0 = 0.5
  red  = (255×0.5) / 0.5 = 255
                            ↑ still pure red
  alpha = 0.5 → 128
    

    Colors stored this way are called straight alpha. Many renderers store colors already multiplied by alpha instead (premultiplied alpha), because then the formula needs no division. Porter and Duff wrote "over" for premultiplied colors in the paper; the formula above is the same equation with the division put back so it works on straight colors. Browsers follow the W3C Compositing and Blending spec, which names this operator source-over.
    

    Study buddy: "Without giving me code, walk me through Porter–Duff 'over' with three cases I can check by hand, then explain straight versus premultiplied alpha with an analogy." Ask Claude · Ask ChatGPT
    

    Gradients: one color per position
    

    A gradient answers one question per pixel: how far along am I, from 0 to 1? Then it mixes the two colors by that amount:
    

      mixColor(a, b, t) = a + (b − a) × t
  (for each of R, G, B and A)

  t = 0      ██ a
  t = 0.25   ██
  t = 0.5    ██ halfway
  t = 0.75   ██
  t = 1      ██ b
    

    A vertical gradient gets t from the row. A radial gradient gets t from distance to a center point. Dividing each axis by its own radius (rx, ry) stretches the circle into an ellipse.
    

    That's exactly what CSS does: radial-gradient(), defined in the CSS Images spec, which says the first size is the horizontal radius and the second the vertical, each as a percentage of the box. KineticIntro's background is written in CSS as:
    

      radial-gradient(70% 60% at 50% 38%,
                  └rx ry┘    └cx cy┘
                  #1A2740, #0B0D12)
                  └inner┘  └outer┘

  on a 1080 × 1920 frame:
    rx = 756    ry = 1152
    cx = 540    cy = 729.6

      Under the hood
      

      Two kinds of fonts
      

      Bitmap fonts store each character as a grid of on/off pixels. Arcade machines, early terminals and the first Macintosh used them; Susan Kare drew the original Mac fonts on graph paper in 1983–84. They're simple and fast, but they only look right at one size.
      

      Outline fonts (TrueType, OpenType) store each character as curves, so they can be drawn at any size. Drawing one means rasterizing the curves into pixels with antialiasing, which is the "which pixels does this shape cover?" problem from layer 01, done very well. That's what the browser does when you write font-size: 150px.
      

      You're building a bitmap font renderer because it shows the whole pipeline with no magic: character → lookup → grid → pixels.
      

      Study buddy: "Explain how outline fonts get rasterized, connecting it to the pixel-center rule I learned in layer 01." Ask Claude · Ask ChatGPT
      

      The font file
      

      lib/font5x7.js is the font. Every glyph is 7 rows of 5 cells:
      

         MS.FONT_5x7.N  =     drawn at scale 3:
   [ "#...#",           ■■■         ■■■
     "##..#",           ■■■■■■      ■■■
     "#.#.#",           ■■■   ■■■   ■■■
     "#..##",   ──►     ■■■      ■■■■■■
     "#...#",           ■■■         ■■■
     "#...#",           ■■■         ■■■
     "#...#" ]          ■■■         ■■■
                        (each # becomes
                         a 3 × 3 block)
      

      Reading it is a nested loop: for each row r, for each column c, if the cell is #, fill a scale × scale square at (x + c × scale, y + r × scale). Scaling by repeating each pixel as a block like this is called nearest-neighbor scaling. It's why pixel art stays crisp.
      

      Laying out a line
      

      Text layout is the job of deciding where each glyph goes. Ours is the simplest possible version:
      

         x
   │◄─ 5 ─►│◄1►│◄─ 5 ─►│◄1►│◄─ 5 ─►│
   ┌───────┐   ┌───────┐   ┌───────┐
   │   H   │   │   I   │   │   !   │
   └───────┘   └───────┘   └───────┘
   ◄─────── measureText = 17 ──────►

   one glyph = 5 cells
   tracking  = gap between glyphs
   width     = 3 × 5 + 2 × 1 = 17 cells
             (× scale for pixels)
      

      • Advance is how far you move right after each glyph: its width plus the tracking.
      • Tracking is uniform extra space between glyphs, so none after the last one (CSS calls it letter-spacing). Kerning, which tightens specific pairs like "AV", is different; our font skips it.
      

      Alignment needs measuring first. To center text on x, you need its total width before drawing the first glyph, so the left edge is x − width / 2. Real layout engines work in the same two passes: measure everything, then place everything. KineticIntro centers every word, so you'll use this constantly.
      

      Study buddy: "Ask me questions until I can explain the difference between advance, tracking and kerning. No code." Ask Claude · Ask ChatGPT
      

      Characters are trickier than they look
      

      • Case. The font has only uppercase. Mapping "g" to "G" (with toUpperCase) is a tiny case of what real fonts do with fallback: when the font lacks a character, find a substitute.
      • Missing characters. When there's no substitute, show tofu: an empty box. (Google's font family Noto is named for "no more tofu".) Tofu is ugly on purpose. It tells you something is missing instead of silently skipping it.
      • What counts as one character? "MOTION·STUDIO" has 13 characters, and · is one of them. But try "👋".length in the console: it says 2. JavaScript strings count 16-bit units (String.length), and characters beyond the first 65,536 take two, called a surrogate pair in Unicode's UTF-16 encoding. for...of and spread ([...text]) walk real characters. A plain for (let i = 0; i < text.length; i++) splits that emoji in half. Pick your loop carefully.

In Inter, the font it uses, capitals are about 73% of that, so roughly 110 px tall. Our capitals are 7 cells tall, so a scale of about 16 matches. Can ANIMATE. fit across 1080 pixels at scale 16 with tracking 1? How large can the scale get before it doesn't? Work it out with measureText once it passes.

        A video is a function from frame numbers to pictures.

        Everything so far draws one picture. KineticIntro is 180 of them, shown 30 a second for six seconds. This layer adds time, though not the way you might expect: instead of nudging things a little on every tick, you'll describe each frame as a function of its number, n. That one decision, which Remotion is built on, is what lets a video jump to any frame, render in any order, and come out the same every time.
        

        Under the hood
        

        Motion is still pictures, fast
        

        Show still pictures quickly enough and your eye reads them as movement. Film shows 24 a second, most web video 30 or 60. That rate is the frame rate, in frames per second (fps). Frame n is on screen from n / fps seconds until the next frame starts:
        

          time (ms), at 30 fps
  0        33.3      66.7      100
  │ frame 0 │ frame 1 │ frame 2 │ frame 3 …
  └────┬────┘
       └─ 1000 ÷ 30 = 33.3 ms
        

        So converting is multiplying or dividing by fps: 1.5 seconds at 30 fps is 45 frames, and 45 frames is 1.5 seconds. Only one direction needs rounding, because a clip can't last half a frame.
        

        frame = f(n)
        

        There are two ways to make a ball move. One keeps state and changes it on every tick: x = x + 2. The other computes the picture straight from the frame number: x = 2 × n.
        

          by mutation:   tick → x += 2 → draw
                 frame 40 depends on frames
                 0–39 having run, in order

  by f(n):       n    → x = 2n → draw
                 frame 40 depends only on 40
        

        The second way wins everywhere that matters. A timeline can jump to frame 140 without playing 0–139. Frames can render out of order, or in parallel: Remotion splits a long video across many CPU cores or cloud machines. And the same n always gives the same picture, so a frame can be tested like any other function.
        

        A composition packages that function with what a player needs to know: width, height, fps, durationInFrames, and render(frame, n). Those are the same props as Remotion's <Composition>. KineticIntro's are 1080 × 1920, 30 fps, 180 frames. renderFrame gives render a brand-new, empty frame every time, so a frame can't depend on what was drawn before it.

          screen (60 Hz)  │  │  │  │  │  │  │  │  │
  video (30 fps)  │  0  │  1  │  2  │  3  │

  screen: a refresh every 16.7 ms
  video:  a frame every 33.3 ms
  → each frame is shown on two refreshes

          Between frames 140 and 172, the sweep travels from −20% to 130% of the way across the logo, and before and after that it stays put. By the end of this layer you'll have written interpolate yourself, options and all, plus a version for colors.
          

          Under the hood
          

          Keyframes and in-betweens
          

          In hand-drawn animation, a lead animator drew the keyframes, the poses that matter, and assistants called in-betweeners drew every frame between them. Software took over that job, now called tweening: you say where something is at a few moments, and the computer fills in the rest.
          

          The simplest way to fill in is a straight line. lerp, short for linear interpolation, walks a fraction t of the way from a to b:
          

            lerp(a, b, t) = a + (b − a) × t

  t: 0     0.25  0.5         1          1.5
     40 ── 50 ── 60 ──────── 80 · · · · 100
     a                       b
          

          t is a fraction, not a frame: 0 is the start, 1 is the end, 0.5 is halfway. Nothing stops it going past 1 or below 0; the line just keeps going. You've already written one: layer 01's mixColor is a lerp on four channels at once.
          

          Map, don't move
          

          inverseLerp runs lerp backwards: given a value, which t gives it? Put the two together and you can map any range onto any other. Say a word fades in between frames 30 and 50, and you want its opacity at frame 35:
          

            frames    30 ────●─────────── 50
                  35
  opacity    0 ────●───────────  1

  frames:  inverseLerp(30, 50, 35) = 0.25
  opacity: lerp(0, 1, 0.25)        = 0.25
          

          First turn the input into a fraction of its range, then turn that fraction into a point in the output range. For two keyframes, that's all interpolate does. Notice what's missing: nothing is stored between frames. The opacity at frame 35 comes from 35 alone, which is exactly what layer 03's frame = f(n) asked for.
          

          Study buddy: "Ask me questions until I can explain why interpolate is inverseLerp followed by lerp, using a fade-out as the example. No code." Ask Claude · Ask ChatGPT
          

          Many keyframes
          

          With more than two keyframes, the ranges become a chain of segments. Find the segment the input falls in, then map within that segment alone:
          

            inputRange  0 ────── 30 ── 50 ──────── 90
  outputRange 0        100   60          60
  segment     └─── 0 ───┘└ 1 ─┘└──── 2 ───┘

  input 40 falls in segment 1:
    t = (40 − 30) / (50 − 30) = 0.5
    output = lerp(100, 60, 0.5) = 80
          

          Keyframes don't have to be evenly spaced, and in real animation they rarely are: each word in KineticIntro takes 26 frames to come in and 22 to leave. What interpolate does insist on is that the inputs are strictly increasing. If they weren't, one input could sit inside two segments at once, and there'd be no single right answer. The outputs can go up, down, or both.
          

          Past the ends
          

          Before the first keyframe and after the last, interpolate has to make something up. That's extrapolation. Say a word scales up from 0.8 to 1 between frames 0 and 10 (KineticIntro's words start at 80% size). What's its scale at frame 20?
          

            scale
   1.2 ┤                    ·   "extend"
   1.1 ┤               ·
   1.0 ┤          ●━━━━━━━━━━━━ "clamp"
   0.9 ┤     ·
   0.8 ┤●
       └┬─────────┬─────────┬──▶ frame
        0        10        20

  ●        a keyframe
  "extend" keeps going along the end
           segment's line
  "clamp"  holds the end value
          

          • "extend", Remotion's default, keeps going along the end segment's line: 1.2, and still growing. With several keyframes, "the end segment" means the first segment before the first keyframe and the last one after the last keyframe.
          • "clamp" holds the end value: 1.
          • "identity" returns the input itself: 20. It only makes sense when input and output measure the same thing.
          

          extrapolateLeft and extrapolateRight choose separately for each end. "extend" is the honest mathematical continuation, but anything with a natural limit, like opacity, a progress bar or a fade, needs "clamp". KineticIntro clamps every single call.
          

          Easing plugs in at t
          

          One more option, easing, is a function that reshapes t before it's mapped to the output. It takes the progress through the segment and returns a new progress:
          

            t → t        even steps
  ●────●────●────●────●────●────●────●────●
  ●●─●──●───●─────●──────●───────●────────●
  t → t × t    slow start, fast finish
          

          Each dot is where the value is after another eighth of the time. Because easing works on t, the start and end don't move: t = 0 still gives the first output and t = 1 the last. Easing only changes when the value gets there. With several keyframes, every segment gets its own trip from 0 to 1, so the easing starts over at each keyframe. Past the ends, with "extend", t goes below 0 or above 1, and the easing is applied to it there too: with t × t, the extension curves instead of running straight. Layer 05 builds real easing curves; this layer just calls whatever function it's given.
          

          Colors are four numbers
          

          interpolateColors blends colors one channel at a time: red with red, green with green, blue with blue, alpha with alpha, each its own interpolation over the same input range. Two things differ from plain numbers:
          

          • It always clamps. There's no color past "fully red" to extend into; the channel would leave 0–255.
          • It rounds. A channel is a whole byte. A Uint8ClampedArray would round for you, but it sends exact halves to the nearest even number (layer 00's bonus). Rounding with Math.round yourself sends them up instead: 128.5 becomes 129, where a clamped array would give 128.
          

          Remotion's own interpolateColors() works the same way: channel by channel, clamped at both ends, rounded.

Those four numbers are the same ones CSS takes in cubic-bezier(). By the end of this layer you'll turn any four numbers into an easing function, the way a browser does, with a little numerical root-finding.
            

            Under the hood
            

            Why ease
            

            Nothing in the real world starts or stops instantly. A ball rolling to a stop slows down; a car pulling away speeds up. Linear motion jumps to full speed on the first frame and halts dead on the last, and our eyes read that as mechanical. An easing function fixes this by changing when the value gets where it's going: it takes the fraction of the time that has passed, x, and returns the fraction of the distance covered, y. It starts at (0, 0) and ends at (1, 1), and the shape between is the personality.
            

            CSS describes that shape with a cubic Bézier curve and two control points, P1 = (x1, y1) and P2 = (x2, y2). Its keywords are just named curves: ease is cubic-bezier(0.25, 0.1, 0.25, 1), ease-in is (0.42, 0, 1, 1), ease-out is (0, 0, 0.58, 1).
            

            A Bézier curve is lerps of lerps
            

            In 1959, Paul de Casteljau, a mathematician at Citroën, found a way to describe smooth car-body curves to a computer; Pierre Bézier at Renault published the same curves a few years later, and they took his name. De Casteljau's way of computing a point on the curve uses nothing but layer 04's lerp. For an easing curve, the four control values along one axis are 0, p1, p2 and 1:
            

              control values:
  0         p1         p2         1
       ●          ●          ●
             ●         ●
                B(u)

  each ● is u of the way from the value
  on its left to the value on its right,
  one row up
            

            Run it once with the x values and once with the y values, and you get the point (x, y) on the curve at parameter u. Multiply the lerps out and you get a cubic polynomial in u instead, which is how browsers write it. Either way works. bezierSlope is that polynomial's derivative: how fast the curve moves along one axis as u grows.
            

            The catch: u isn't time
            

            As u runs from 0 to 1, the point travels along the curve, but x and y both depend on u. An easing function is asked a different question: at time x, what's y? To answer it, first find the u where the curve's x equals the time you were given, then read the curve's y at that u:
            

              x (time)
  │ solve
  ▼
  u
  │ bezierPoint(y1, y2, u)
  ▼
  y (progress)
            

            There's no tidy formula for that first arrow. (Cubic equations do have a formula, but it's fussy and loses precision.) So browsers find u numerically.
            

            Newton's method
            

            Guess a u, see how far its x is from the target, then use the slope to jump to where a straight line would hit the target: u ← u − error ÷ slope. Here's ease-in (x1 = 0.42, x2 = 1) looking for x = 0.6, starting from the guess u = 0.6:
            

              step  u          x at u       error
  0     0.6        0.76896      +0.169
  1     0.4370     0.58058      −0.0194
  2     0.4525     0.59988      −0.00012
  3     0.452605   0.60000000   −0.000000005

  step  slope   next u = u − error ÷ slope
  0     1.037   0.4370
  1     1.256   0.4525
  2     1.240   0.452605
  3             close enough
            

            The error goes 0.17, 0.02, 0.0001, 0.000000005: each step roughly doubles the number of correct digits. That's Newton's method, and it's usually done in three or four steps.
            

            Study buddy: "Ask me questions until I can explain why Newton's method divides by the slope, and what goes wrong when the slope is nearly zero. Use a curve that isn't an easing curve. No code." Ask Claude · Ask ChatGPT
            

            Bisection, the safety net
            

            Newton's method has a weak spot: where the curve goes flat, the slope is near zero, and dividing by it flings u far away. Bisection can't fail. The curve's x only ever increases, so the answer is always inside a known gap, starting with 0 to 1. Check the middle: if its x is too big, the answer is in the left half; otherwise it's in the right half. Each check halves the gap:
            

              [0 ─────────────────────────────── 1]
  x at 0.5 too big?    keep the left half
  [0 ─────────────── 0.5]
  x at 0.25 too small? keep the right half
          [0.25 ──── 0.5]
  … until the x at the middle is within 1e-7
            

            The gap is in u, but the spec's 1e-7 is about x, and an easing curve's x can change up to 3 times faster than u, so it can take about 25 halvings. It's slow but sure, so real solvers use both. WebKit's UnitBezier, the code behind Safari's CSS animations, takes a first guess from a table of 11 samples, tries up to 4 Newton steps, and bisects if they don't get close enough.
            

            Only x has to behave
            

            CSS insists that x1 and x2 stay between 0 and 1, and it rejects the curve otherwise. Outside that range the curve's x can turn around and run backwards, which would mean time running backwards: one moment x would have three different us and no single answer. That's the same reason layer 04 insisted on increasing keyframes.
            

            The y values have no such rule. A y control point above 1 makes the value overshoot its target and settle back, like cubic-bezier(0.34, 1.56, 0.64, 1); one below 0 makes it back up before it starts, called anticipation. Both are old tricks from hand-drawn animation.

      Layer 06
      
              Springs
              
      
              A spring doesn't know where it's going to be, only what happens next.
              
      Open the workbench ↓

              Builds on: layers 00–05
              

              Easing curves are drawn by hand: someone picks four numbers and the motion follows the shape exactly. A spring is different. You describe a physical object, how stiff it is, how much friction it has and how heavy it is, and the motion is whatever physics says happens. That's why spring motion feels alive, and why Remotion's spring() is one of its most-used functions. KineticIntro itself only uses easing curves; springs are the other half of Remotion's motion toolkit. This layer simulates one, step by step, and finds out how small the steps have to be.
              

              Under the hood
              

              A spring is a rule, not a curve
              

              Picture a weight on a spring, lying on a slippery table. Pull it and let go. Two forces act on it. The spring pulls it back toward where it wants to rest, harder the further away it is: that's Hooke's law. Friction, called damping, pushes against the motion, harder the faster it moves:
              

                            the spring pulls it back
          ┌──────────────┴───────────────┐
  force = −stiffness × (position − target)
        − damping × velocity
          └───────┬────────┘
          friction slows it

  acceleration = force ÷ mass
              

              That's the whole description, and it only says what happens next: given where the weight is and how fast it's moving, here's how its speed is changing. To find out where it is at frame 30, you have to play time forward from the start.
              

              Stepping through time
              

              Playing time forward means taking small steps of dt seconds. Each step uses the force to update the velocity, and the velocity to update the position. The order matters more than it looks:
              

                explicit Euler:
    position += velocity × dt
                └─ the old velocity
    velocity += acceleration × dt

  semi-implicit Euler:
    velocity += acceleration × dt
    position += velocity × dt
                └─ the new velocity
              

              Both look reasonable, and over one step they barely differ. Over thousands of steps, explicit Euler quietly adds energy every time: a spring with no friction swings a little wider each second, forever. Semi-implicit Euler keeps the swing the same size, which is why physics engines use it. It costs nothing extra; it's just the right order.
              

              How small is small enough?
              

              Each step pretends the force stays the same for dt seconds. That's fine while dt is short compared with how fast the spring swings. A spring's natural speed is ω = √(stiffness ÷ mass), in radians per second, and semi-implicit Euler stays stable only while ω × dt is below 2. Past that, every step overshoots a little more than the last, and the numbers explode.
              

              A video frame is far too long a step: at 30 fps, dt is 33 ms, so any spring stiffer than about 3,600 (with mass 1) blows up. This layer steps every 1 ms instead, and frame n is 1000 × n ÷ fps milliseconds in, rounded to the nearest whole step. Notice what that costs: because frame = f(n), working out frame 90 means simulating all 3,000 steps from the start, every time.
              

              Study buddy: "Ask me questions until I can explain why updating the velocity before the position keeps a frictionless spring from gaining energy. No code." Ask Claude · Ask ChatGPT
              

              The damping ratio
              

              Three numbers describe a spring, but its character comes down to one, the damping ratio:
              

                ζ = damping ÷ (2 × √(stiffness × mass))

  ζ below 1   underdamped
    overshoots, bounces, then settles

  ζ = 1       critically damped
    arrives as fast as possible,
    never overshoots

  ζ above 1   overdamped
    creeps in slowly, never overshoots
              

              Remotion's default spring is stiffness 100, damping 10, mass 1, so ζ = 10 ÷ (2 × 10) = 0.5: a little bouncy.
              

              When is it done?
              

              A spring never quite arrives. Each bounce is smaller than the last, but it never reaches exactly zero. So "done" needs a definition: the spring has settled at the first frame from which it stays within some small distance of its target for good. Remotion's measureSpring() uses half a percent of the distance from from to to, and so does settleFrame. "Stays" matters: a bouncy spring can pass through the target zone on its way back out.

      Layer 07
      
                Transforms & blur
                
      
                A matrix is six numbers that say where everything goes.
                
      Open the workbench ↓
    
                
    
                You'll write: translate, scale, rotate, multiply, transformPoint, invert, drawTransformed, boxBlur, blur in src/07-transforms.js
                Builds on: layers 00–06
                

                Each word in KineticIntro arrives the same way: it grows from 80% to full size while it sharpens out of a blur(14px), then keeps pushing slowly toward the camera before it blurs away again. In CSS that's two lines, transform: scale(…) and filter: blur(…), and the browser does the work. In this layer you do the work: matrices that move, scale and turn anything, a way to draw a picture through a matrix without holes or dark edges, and a blur whose cost doesn't depend on how wide it is.
                

                Under the hood
                

                Six numbers move everything
                

                Moving, scaling, rotating and slanting are all the same kind of operation, an affine transform, and six numbers describe any of them. The HTML canvas standard and CSS's matrix() both write them as a, b, c, d, e, f:
                

                  ┌ a  c  e ┐   ┌ x ┐     x' = a·x + c·y + e
  │ b  d  f │ × │ y │     y' = b·x + d·y + f
  └ 0  0  1 ┘   └ 1 ┘
                

                The six numbers are easier to read as three arrows. (e, f) is where the origin (0, 0) lands. (a, b) is where one step along x, the point (1, 0), lands, measured from there; (c, d) is the same for one step along y. Draw those three things and you've drawn the whole transform: every other point follows from them.
                

                  scale(2, 0.5)
  (1, 0) → (2, 0)
  (0, 1) → (0, 0.5)

  ┌────┐
  │    │    →    ┌────────┐
  │    │         └────────┘
  └────┘

  a slant: c = 0.5, the rest as in scale(1)
  (1, 0) → (1, 0)
  (0, 1) → (0.5, 1)

  ┌────┐          ┌────┐
  │    │    →      ╲    ╲
  │    │            ╲    ╲
  └────┘             └────┘
  (y points down, so the bottom moves right)
                

                On a screen, y points down. A rotation that turns +x toward +y therefore looks clockwise, the opposite of the math textbook picture. Canvas and CSS both work this way.
                

                Order matters
                

                A transform made of steps is one matrix: multiplying two matrices gives a single matrix that does both. But which one happens first changes the result. Take the point x = 3:
                

                  scale by 2, then move right 4:  3 → 6 → 10
  move right 4, then scale by 2:  3 → 7 → 14
                

                In multiply(m, n), n happens first. That reads backwards at first, but it's the same order as function calls: in m(n(p)), n runs first.
                

                Order is also how you scale around a point other than the origin. scale(1.04) on its own grows everything away from (0, 0), the top-left corner, so a word in the middle of the screen would drift down and to the right. To grow around the middle, three steps: move the middle to the origin, scale, move it back.
                

                Drawing backwards
                

                To draw a picture through a matrix, the obvious plan is to take every source pixel, move it, and paint it where it lands. Try that with a 3× zoom: neighboring source pixels land 3 pixels apart, and the pixels in between are never painted.
                

                  forward: each source pixel goes somewhere
  █ █ █      →     █ · · █ · · █
                   · · · · · · ·
                   holes

  backward: each destination pixel asks
  "where did I come from?"
  █ █ █      ←     █ █ █ █ █ █ █ █ █
                   (every pixel is filled)
                

                So renderers work backwards: for each pixel of the destination, find the point in the source that lands on it, and take the color from there. That needs the matrix that undoes m, its inverse. Not every matrix has one. The number a·d − b·c (the determinant) says how much the matrix scales areas. (A negative one means it also mirrors; only 0 can't be undone.) When it's 0, the matrix squashes everything onto a line or a point, and there's no way back: many source points land on the same spot.
                

                Between the pixels
                

                The point you find in the source is almost never exactly on a pixel. Pixel (x, y) is a little square from (x, y) to (x + 1, y + 1), so its center is (x + 0.5, y + 0.5). A point between centers takes a little of each of the four nearest pixels, more from the nearer ones. That's bilinear sampling: blend along x, then along y.
                

                  center (3.5, 0.5)   center (4.5, 0.5)
         ●─────×─────────────●
               ↑ the sample (×), 30% of the
                 way from left to right,
                 gets 70% of the left pixel
                 and 30% of the right
                

                Nearest-neighbor sampling (just take the closest pixel) is faster, but edges turn into stairs as a picture rotates, and a slow move jumps a whole pixel at a time. Bilinear sampling lets a picture move by a fraction of a pixel, which matters for slow motion like KineticIntro's 4% push.
                

                Study buddy: "Ask me questions until I can explain why drawing through a matrix works backwards, from destination pixels to source points, and what the determinant has to do with it. No code." Ask Claude · Ask ChatGPT
                

                Edges without dark fringes
                

                Bilinear sampling at the edge of a picture mixes a pixel of the picture with a transparent pixel outside it. Layer 01 showed that a transparent pixel is stored as [0, 0, 0, 0]: "black, invisible". Average a white pixel with it channel by channel, and you get [128, 128, 128, 128], a half-transparent grey. The black that was never visible has leaked in, and every edge gets a dark fringe.
                

                  straight average
  [255,255,255,255]
  [  0,  0,  0,  0]
  ────────────────── ÷ 2
  [128,128,128,128]  grey

  premultiplied average
  color × alpha:  255·255 and 0·0
  alpha:          255 and 0
  ─────────────────────────────────────
  alpha: (255 + 0) ÷ 2 = 128
  color: total color ÷ total alpha
         = (255·255 + 0) ÷ (255 + 0)
         = 255: still white
                

                The fix is to average premultiplied colors: weight each pixel's color by its alpha, so a transparent pixel adds nothing to the color, only to the alpha. Divide by the total alpha at the end to get a plain color back. Browsers keep pixels premultiplied inside, partly for this reason.
                

                A blur that doesn't care how big it is
                

                The simplest blur is a box blur: each pixel becomes the average of the pixels in a box around it. A box of radius r is 2r + 1 pixels wide. Two tricks make it fast:
                

                  1. rows, then columns:
     blurring every row, then every column,
     gives the same result as averaging the
     whole square, but each pixel adds up
     2·(2r + 1) values instead of (2r + 1)².

  2. a running sum:
     moving the box one pixel right changes
     only its two ends.
     ┌───────────┐
     │ a b c d e │ f
     └───────────┘
     sum(b…f) = sum(a…e) − a + f
     Two operations per pixel,
     whether r is 1 or 100.
                

                Pixels outside the frame count as transparent, so a blur fades a picture out at its edges instead of smearing the edge pixels outward. Average premultiplied, for the same reason as above.
                

                Three boxes make a bell
                

                A box blur looks boxy: a single bright dot becomes a flat square. Box-blur that square again and the profile becomes a triangle; a third time and it's a smooth bell, very close to a Gaussian. That's the central limit theorem at work: adding up a few independent random amounts quickly gives a bell curve.
                

                  one box        two boxes        three boxes
  ▁▁███▁▁        ▁▃▆█▆▃▁          ▁▂▅█▅▂▁
                

                A Gaussian blur's size is its standard deviation, σ (sigma), in pixels, and that's what CSS's blur() takes: blur(14px) means σ = 14. To pick r for three boxes, match the spread. A box of radius r has a variance (σ²) of r(r + 1) ÷ 3, and variances add up when blurs are stacked, so three boxes give r(r + 1). Setting that equal to σ² and solving gives the radius in the comment above blur in src/07-transforms.js. For σ = 5 it's round((√101 − 1) ÷ 2) = round(4.525) = 5.

                  Under the hood
                  

                  Real text is a picture the browser draws for you
                  

                  Layer 02's bitmap font had one size and no curves. Real fonts are outlines, and the browser's text engine turns an outline into pixels, with smooth edges, at any size. You ask for it through a canvas: set ctx.font, then call fillText. The font is a string in the same order as CSS's font shorthand: weight, then size, then family, like "900 150px Inter".

                  Every layer has its own clock
                  

                  A scene doesn't care what time the video says it is. It cares how long it has been running. Remotion's <Sequence> gives each part of a video its own frame counter: inside <Sequence from={30} durationInFrames={20}>, video frame 30 is frame 0, and outside frames 30–49 the sequence isn't drawn at all.
                  

                   video frame: 0 ··· 29 30 31 ··· 49 50 ···
 sequence:    (not on)  0  1 ··· 19 (not on)
                  

                  <Series> works out the froms for you by putting sequences back to back. An offset moves a sequence earlier (negative) or later (positive), and since each sequence starts where the one before it ends, everything after it moves too.
                  

                  A camera is the world moving the other way
                  

                  Pan a camera to the right and everything on screen slides left. Turn it clockwise and the world turns counterclockwise. A camera is the opposite of an object: an object's matrix moves it into the world, and a camera's matrix moves the world into the camera's view. Whatever the camera does, the world does the reverse, and the point it looks at has to end up in the middle of the screen. Every layer's own matrix gets multiplied by the camera's, so one camera move moves the whole scene.
                  

                  Layers, masks, and the order of effects

                    Reading a component as math

  (not to scale)
  frame:   38 40           66         88 90

                    Blend modes: changing what "over" means
                    

                    Layer 01's blend put the new color over the old one. CSS's mix-blend-mode keeps that recipe but changes one ingredient: where the two colors overlap, the result is B(backdrop, source) instead of just the source. The general formula mixes three parts, by how much each color covers:
                    

                      only the source shows:
    (1 − αb) × αs × Cs

  both overlap:
    αb × αs × B(Cb, Cs)
              ↑ the blend mode lives here

  only the backdrop shows:
    (1 − αs) × αb × Cb
                    

                    With B(Cb, Cs) = Cs that's exactly your blendPixel. That's why lockupLayer blends the sweep into its sprite, not into the frame.
                    

                    A shadow is a blur
                    

                    The vignette is box-shadow: inset 0 0 280px rgba(0, 0, 0, 0.7). An inset shadow is the shadow of everything outside the box, falling inward. CSS Backgrounds says a blur radius of 280px means a Gaussian blur with σ = 140, half the radius. So: make a frame that's black everywhere except a hole the size of the screen, blur it with your three box blurs, and keep the middle. The margin around the hole must be wider than the blur reaches, or the far edge of the black would fade in too, and a blur reaches a few σ, which is why the spec asks for a little more than 3σ. Watch the units: filter: blur(16px) means σ = 16, but a box-shadow blur radius of 280px means σ = 140.

                      Under the hood
                      

                      Codec and container
                      

                      An MP4 is a container: a box of boxes that holds the frames, plus a table of contents. The frames inside are compressed by a codec, here H.264, the most widely played video format there is. The two are separate: the same H.264 frames could go in a different container, and an MP4 can hold other codecs.
                      

                        your frames       RGBA pixels (~330 KB
    │               each at 216 × 384)
    ▼
  encoder (H.264,   compresses each frame
  by WebCodecs)
    │
    ▼
  chunks            one per frame, a few KB
    │
    ▼
  container (MP4,   where and when each
  by you)           chunk is, so a player
    │               can find and time it
    ▼
  file
                      

                      H.264 frames can be laid out two ways. Live streams use "Annex B", with a start code between the pieces of each frame. MP4 wants each piece prefixed with its length instead, and the encoder's setup (its SPS and PPS) stored once, in an avcC record. The provided encoder asks WebCodecs for exactly that layout; Annex B bytes in an MP4 won't play.
                      

                      Boxes all the way down
                      

                      The format comes from Apple's QuickTime and is standardized as the ISO base media file format (ISO/IEC 14496-12). It's built from one idea: a box (QuickTime calls it an atom) is 4 bytes of size, 4 letters of type, and then its contents, which can be more boxes.
                      

                        ┌─────────────┬────────────┬─────────────┐
  │ size (u32)  │ type       │ contents:   │
  │             │ (4 ASCII)  │ data or     │
  │             │            │ more boxes  │
  ├─────────────┼────────────┼─────────────┤
  │ 00 00 00 08 │ f  r  e  e │ (none: an   │
  │             │            │ empty box)  │
  └─────────────┴────────────┴─────────────┘
     the size counts the whole box,
     these 8 header bytes included
                      

                      A program that doesn't know a box type can still skip it: read the size, jump ahead. It's one reason the format has lasted since QuickTime's first release in 1991. Many boxes are full boxes, whose contents start with a version byte and 3 bytes of flags, so the format can change without breaking old readers.
                      

                      Biggest byte first
                      

                      Every number is big-endian: the most significant byte comes first, the way you write digits. 300 as a u32 is 00 00 01 2C. Your computer's processor is almost certainly little-endian and would store it backwards, which is why u32 builds the bytes by hand with shifts and masks instead of copying memory. Network protocols use big-endian too; it's often called "network byte order".

  │ mdat hdr │

  │ chunk 1  │
  │          │
  ├──────────┤ ◄ offset 2 =

  ├──────────┤

  ├──────────┤
  │  · · ·   │
  ├──────────┤
  │ moov     │
  └──────────┘
                      

                      When: timescales and runs
                      

                      MP4 counts time in whole ticks of a timescale: ticks per second. This file's media uses 90000, a habit from MPEG broadcasting, because it divides evenly by 24, 25, 30, 50 and 60, so common frame rates get whole-number frame durations. At 30 fps, every frame lasts 3000 ticks. stts stores durations as runs, "180 samples of 3000", so a constant frame rate costs 8 bytes no matter how long the video is. That's run-length encoding, the same trick as "A × 3" instead of "AAA".
                      

                      The movie header (mvhd) has its own clock too. This file sets it to milliseconds (timescale 1000), and the track header (tkhd) gives the track's length on that clock.
                      

                      Which: key frames
                      

                      H.264 saves most of its space by storing most frames as differences from earlier ones. A key frame stands alone; the frames after it are built from it. A player can only start decoding at a key frame, so jumping to 0:04 means finding the key frame at or before it. stss lists them, by sample number, counting from 1 (a file with no stss at all says every frame is a key frame). The provided encoder makes one every two seconds: fewer key frames make a smaller file, and more make seeking quicker.
                      

                      The order of the boxes
                      

                      Your file puts mdat before moov. That's the easy order: when you write the offsets you already know exactly where everything is. It's also how a camera records: it can't write the table of contents until it stops filming. Its one downside is that a player streaming the file over a network has to fetch the end before it can start. Moving moov to the front ("fast start") fixes that, but then the offsets have to skip the moov too.
